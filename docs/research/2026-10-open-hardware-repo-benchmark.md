# Research: how open-hardware projects organize and publish their repositories

**Date:** 2026-10-21 · **Status:** research input, not a decision · **Scope:** repository granularity, folder layout, KiCad / FreeCAD / Blender library management, hardware revision versioning, generated outputs, CI, Git LFS, licensing and documentation, benchmarked across ~30 open-hardware projects. Feeds the per-repo scaffold for OpenDAP (mainboard, faceplates, case, HAT standard plus 7 HATs, firmware, Rust system software, distro) and the org-wide part libraries.

> Section 6 is **recommendations only**. Nothing in it has been decided.
> **UNVERIFIED** means the claim could not be confirmed from a primary source during this research.
> Method: repository trees, `.gitattributes`, `.gitmodules`, lib tables, CI files, tags and release assets were read through the GitHub REST API (`gh api`), the GitLab v4 API (gitlab.com, source.mnt.re) and the projects' web pages, on 2026-10-21. Sizes are the `size` field from the GitHub API (KB, approximate).

## 2. Recurring patterns (with counts)

Counts cover the projects in the table that publish something. The names are listed so each count can be checked.

### 2.1 Repository granularity

- **Hybrid** (device hardware plus its MCU firmware together; OS, handbook or libraries elsewhere): MNT Reform, Pocket Reform, Precursor, Flipper One, Prusa, Antmicro, SparkFun → **7**.
- **Monorepo** (hardware, firmware/gateware and host software together): HackRF, Glasgow, LibreVNA, ThunderScope, Olimex, Mutable Instruments, Corne, ClockworkPi → **8**. All are single-product or single-family instrument projects.
- **One repo per product or module**: Framework, SparkFun, Adafruit, Antmicro, Befaco, Prusa, BeagleBoard → **7**.
- **The OS / distro is always a separate repo** when the project ships a Linux OS: MNT (`reform-system-image`), Flipper One (`flipperone-linux-build-scripts`), Precursor (`xous-core`) → **3 of 3**.
- **Handbook / user docs as a separate repo**: MNT (both products) → **2**. Others keep `docs/` in the main repo (HackRF, Glasgow, ThunderScope, LibreVNA, Antmicro, OpenFlexure, SparkFun).

### 2.2 Folder layout

- A top-level split by discipline (`hardware/` or `Hardware/`, `firmware/`, `software/` or `host/`, `docs/`) in **8** repos: HackRF, Glasgow, LibreVNA, ThunderScope, Olimex, Ploopy, Befaco/muxlicer, SparkFun products.
- **One folder per board** under the hardware folder in **7**: HackRF, Glasgow, ThunderScope, MNT (both), Precursor, Olimex.
- **KiCad project at the repo root** (one board per repo): Antmicro, SparkFun Default Setup, KDT template → **3**.
- Mechanics as a **sibling folder of the board** (`cases/`, `Mechanical/`): Glasgow, Framework, Corne, HackRF → **4**. As a **separate repo**: Prusa, Flipper One, Antmicro enclosure → **3**.

### 2.3 KiCad library management

- **Project-local libraries** (`*.pretty`, `*.kicad_sym`, 3D folder, `${KIPRJMOD}` paths): MNT (both), ThunderScope, LibreVNA, Framework, HackRF (partly), Glasgow (repo-wide), Prusa Buddy, MNT SoM template → **9**. This is by far the most common pattern.
- **A shared org library in its own repo**: GSG `gsg-kicad-lib` (submodule), Antmicro `hardware-components` (generated, global tables), SparkFun `SparkFun-KiCad-Libraries` (env var plus PCM), foostan `kbd` (vendored copy in Corne) → **4**.
- How consumers reference it: **git submodule plus `${KIPRJMOD}/../…`** (HackRF; Ergogen footprints) = 2. **Custom path variable** (`SPARKFUN_KICAD_LIBRARY`) = 1. **Global lib table / install** (Antmicro) = 1. **Vendored copy** (Corne) = 1. **PCM package** (SparkFun since fall 2025; KiKit; iBOM) = 3 publishers.
- **Lib tables in git**: committed by HackRF, ThunderScope, LibreVNA, Framework, Antmicro (empty), Corne. **Ignored** by MNT, which breaks the project for anyone who lacks MNT's global tables.
- **KLC-style lint in CI**: only the KiCad official libraries.

### 2.4 Hardware revision versioning

- **Folder per revision** (several revisions side by side in `main`): Glasgow, Precursor, Olimex, ThunderScope (Rev5.3), Prusa Buddy (`rev.1.0.0`), Flipper One mechanics (`CURRENT/`/`OLD/`), MNT (per board generation) → **7**.
- **Git tags per hardware revision**: Antmicro (`rev.1.3.4`), BeagleBone Black (`rev_c3`), Corne (`v4.1`), Prusa (`R6`), NanoVNA V2 (`prototype-v2_2`) → **5**.
- **Revision only in file names**: ClockworkPi, Mutable Instruments, Pine64, Adafruit, Framework → **5**.
- **Explicit compatibility semantics in the version**: Flipper One `<LETTER>.<NUMBER>` (letter = not mechanically compatible) → **1**. This is the only scheme found that tells accessory makers what still fits.
- **Firmware artifacts named by hardware revision or variant**: LibreVNA (`hw-rev-B`), NanoVNA-H (H/H4 × MS/SI/ZK), Prusa (`MK25S-RAMBo13a`), OpenMV (per board), MNT LPC firmware (`firmware-20_R3`, `-25_R2`, `-30_R1`) → **5**.

### 2.5 What is committed and what is generated

- **Fab outputs committed to git**: Glasgow, ThunderScope, LibreVNA, Precursor, Olimex, Corne, SparkFun products, ClockworkPi, NanoVNA V2, BeagleBone → **10**.
- **Fab outputs generated only (CI or release assets)**: Antmicro (release assets), OpenFlexure (STL in CI) → **2**.
- **Hardware release assets on GitHub/GitLab Releases**: Antmicro (PDF, STEP, renders), Prusa (STL zip) → **2**. Firmware release assets are common: LibreVNA, NanoVNA-H, NanoVNA-D, Prusa-Firmware, OpenMV, MNT, Befaco, PicoCalc, xous-core → **9**.
- **Editor state committed by mistake** (`.kicad_prl`, `fp-info-cache`): ThunderScope, LibreVNA, Framework InputModules → **3**. Ignored by Glasgow, Antmicro and MNT.
- **Reproducibility checks on committed binaries**: Glasgow rebuilds firmware in CI and fails if it differs from the committed file → **1**. MNT pins `SOURCE_DATE_EPOCH` → **1**.

### 2.6 CI

- **CI that runs ERC/DRC or builds fab outputs from KiCad sources: no flagship project found doing it in public CI.** ThunderScope commits a KiCad 9 jobset that does it, but runs it by hand. Antmicro's template is private. Small projects do use KiBot or `kicad-cli` actions ([code search sample](https://github.com/search?q=%22uses%3A+INTI-CMNB%2FKiBot%22&type=code)).

## 3. Anti-patterns and pain points

Each item names the project where it was observed, with a citation.

1. **Lib tables ignored in git.** MNT's `.gitignore` excludes `sym-lib-table` and `fp-lib-table` ([.gitignore](https://source.mnt.re/reform/reform/-/blob/main/.gitignore)). A fresh clone depends on the cache or on the user's global tables to resolve symbols and footprints.
2. **Editor-local files committed.** `.kicad_prl` and `fp-info-cache` are in ThunderScope ([Rev5.3](https://github.com/EEVengers/ThunderScope/tree/master/Hardware/Thunderscope_Rev5.3)), LibreVNA ([Hardware/Kicad](https://github.com/jankae/LibreVNA/tree/master/Hardware/Kicad)) and Framework InputModules. They cause noisy diffs. Glasgow and Antmicro ignore them explicitly ([Glasgow hardware/.gitignore](https://github.com/GlasgowEmbedded/glasgow/blob/main/hardware/.gitignore), [Antmicro .gitignore](https://github.com/antmicro/jetson-orin-baseboard/blob/main/.gitignore)).
3. **Generated outputs in git make repos heavy and can go stale.** ThunderScope is ~1.19 GB with 243 `.webp` files and committed fab zips. The Olimex tree holds 337 Gerber files. Nothing guarantees that committed Gerbers match the committed board. Glasgow is the only project that checks a committed artifact against a fresh build, and it does so for firmware, not Gerbers.
4. **Library repos become huge.** The FreeCAD-library maintainers warn "the library is huge in size (+/- 5 Gb) and therefore might take a very long time to download" ([README](https://github.com/FreeCAD/FreeCAD-library)). Antmicro `hardware-components` is ~14.5 GB without LFS. Both are hard to use as a submodule or to clone in CI.
5. **KiCad file diffs and merges.** Small edits reshuffle `.kicad_pcb`. Text merges can corrupt the board. Raw diffs show formatting, not electrical changes ([KiCad forum: line order](https://forum.kicad.info/t/git-friendly-line-order-in-kicad-pcb-files/29518), [corruption during merge](https://forum.kicad.info/t/pcb-file-gets-corrupted-during-git-merge/30802), [version control and merging](https://forum.kicad.info/t/kicad-version-control-and-merging/1975?page=3)). Visual diff tools exist ([KiRI](https://github.com/leoheck/kiri), KiBot `diff`/`kiri` outputs).
6. **FreeCAD files are opaque zips.** Git stores a full copy of every `.FCStd` version and cannot diff it. `fcinfo` as a textconv driver gives a readable diff but does not reduce storage ([FreeCAD wiki](https://wiki.freecad.org/Arch_Git), [blog](https://blog.lambda.cx/posts/freecad-and-git/)). FreeCAD-library sets `*.FCStd diff=fcinfo` ([.gitattributes](https://github.com/FreeCAD/FreeCAD-library/blob/master/.gitattributes)).
7. **Proprietary sources limit reuse.** Precursor ships Altium and SolidWorks sources ([tree](https://github.com/betrusted-io/betrusted-hardware)). Prusa MINI ships Inventor `.ipt` ([SOURCE](https://github.com/prusa3d/Original-Prusa-MINI/tree/master/SOURCE)). Flipper One keeps PCB sources in Altium 365, outside git ([README](https://github.com/flipperdevices/flipperone-hardware/blob/dev/README.md)). Contributors without those tools can only use the exported STEP, PDF or Gerber files.
8. **"Open" that is only PDFs.** ClockworkPi, Pine64, Framework mainboards and Flipper Zero publish schematics or interface drawings only. Flipper One publishes the body as "a single solid shell with an empty interior … intentionally to prevent direct copying" ([mechanics README](https://github.com/flipperdevices/flipperone-mechanics/blob/dev/README.md)). This is enough for accessory makers, not for derivative boards.
9. **Missing license files.** 7 repos have none (§2.9). Legally that means "all rights reserved".
10. **Library moves break links.** The KiCad libraries moved to GitLab and the GitHub repos are archived (last push 2021; [kicad-symbols](https://github.com/KiCad/kicad-symbols)). `edy555/NanoVNA` now returns 404, and the Purism hardware repos are not reachable through the API. Submodule URLs and docs links that point at a moved host rot.
11. **PCM friction.** SparkFun needs two release zips, "with-pcm" and "without-pcm", because PCM adds a user-configurable `PCM_` nickname prefix. Users of KiCad 10 must restart KiCad after installing ([README](https://github.com/sparkfun/SparkFun-KiCad-Libraries/blob/main/README.md)).
12. **Board revisions with known pitfalls stay visible next to good ones.** Glasgow's README has to warn not to build revA/revB ([boards README](https://github.com/GlasgowEmbedded/glasgow/blob/main/hardware/boards/glasgow/README.md)). Folder-per-rev keeps obsolete revisions one click away.
13. **Manual steps for renders.** Glasgow documents a manual KiCad raytrace recipe for its renders, with a note on symlinks not working on GitHub Pages ([boards README](https://github.com/GlasgowEmbedded/glasgow/blob/main/hardware/boards/glasgow/README.md)). The MNT iBOM depends on a plugin path on the developer's machine (`~/.kicad_plugins/…`) ([build.sh](https://source.mnt.re/reform/reform/-/blob/main/reform2-ibom/build.sh)).
14. **GitHub limits.** GitHub warns above 50 MiB per file, blocks files above 100 MiB, and recommends repos under 1 GB (strongly under 5 GB) ([docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)). The LFS free quota is 10 GiB storage and 10 GiB bandwidth per month, and usage is blocked when it runs out without a payment method ([docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-storage-and-bandwidth-usage)). CI clones count against bandwidth.

### 4.2 PCM mechanics, relevant for a custom repository

- Package types `plugin`, `library`, `colortheme` (v1 schema), plus `fab` and `datasource` in v2. `metadata.json` has `identifier` (reverse-DNS), `type`, `license`, and `versions[]` with `kicad_version`, `status`, `download_sha256`, `download_url`. A repository publishes `repository.json` plus `packages.json`. Libraries install under `KICADx_3RD_PARTY` into `symbols/`, `footprints/` and `3dmodels/` ([dev docs](https://dev-docs.kicad.org/en/addons/)). Users can add a **custom repository URL** in the PCM (UNVERIFIED in the fetched page; widely documented in the PCM UI).
- KiCad path variables set in "Configure Paths" are internal to KiCad, but they can also come from system environment variables. `KIPRJMOD` is set automatically and cannot be redefined ([KiCad 10 docs](https://docs.kicad.org/10.0/en/kicad/kicad.html)).

### 4.3 Patterns in shared libraries

- **Per-tool repos** (KiCad official, SparkFun, GSG, FreeCAD-library) are the majority. **One multi-tool repo** keyed by MPN is used by Antmicro only, and it reached ~14.5 GB.
- **Pinning**: only the submodule users (GSG, Ergogen) pin a library version per design. The env-var and PCM users (SparkFun) get "whatever is installed". SparkFun's own designs follow the library head.
- **Lint**: only KiCad runs KLC in CI; FreeCAD-library relies on written guidelines.
- **3D formats**: STEP is the master format everywhere. KiCad keeps WRL next to STEP for rendering appearance. Antmicro adds glTF and `.blend`. OpenMV ships `.glb` for its viewer. FreeCAD-library keeps `.FCStd` (parametric source) next to `.step`.

## 6. Recommendations for OpenDAP (NOT decisions)

> Everything in this section is a recommendation for the maintainers to accept, change or reject.

### 6.1 Repository map

- **R1. Keep one repo per component, as already planned**: `mainboard`, `faceplates`, `case`, `hat-spec`, `hat-<name>` ×7, `firmware`, `system` (Rust), `distro`. This matches the hybrid and split pattern of MNT, Flipper One, Antmicro and Prusa, and the rule that the OS is always its own repo (§2.1).
- **R2. Put MCU firmware next to its board only when it is board-specific and small** (HAT MCU, faceplate controller), like HackRF, Glasgow and LibreVNA. Keep shared firmware (common HAL, bootloader, protocol crates) in `firmware`, consumed as a crate dependency, not copied.
- **R3. Add org-level repos**: `kicad-lib`, `freecad-lib`, `blender-lib` (see 6.9), `ci` (reusable workflows, see 6.6) and `.github` (default community files).

### 6.2 Per-repo layout (hardware repos)

Recommended skeleton, adapted from HackRF, Glasgow and Antmicro:

```text
<repo>/
├── README.md               # what, status, photo/render, links to release + docs
├── LICENSES/  REUSE.toml   # REUSE, like the toolkit repo
├── electronics/
│   └── <board>/            # one KiCad project per board, fixed path across revisions
│       ├── <board>.kicad_pro / .kicad_sch / .kicad_pcb / .kicad_dru
│       ├── <board>.kicad_jobset        # release outputs, runnable locally and in CI
│       ├── sym-lib-table  fp-lib-table # committed, paths via ${KIPRJMOD}
│       └── lib/            # board-only parts that are not yet promoted to kicad-lib
├── libs/opendap-kicad-lib/ # git submodule, pinned (see 6.9)
├── mechanics/              # FreeCAD sources + exported STEP of interfaces (see 6.4)
├── sims/                   # SPICE / openEMS / thermal setups; results generated, not committed
├── renders/                # Blender scene files only; images are generated
├── firmware/               # only if board-specific (R2)
├── docs/                   # Sphinx or mdBook sources (see 6.8)
├── .kibot.yaml (optional)  # if KiBot is used for iBOM/diff/renders
└── .github/workflows/      # thin callers of opendap/ci reusable workflows
```

- **R4. Use a fixed project path per board** (`electronics/mainboard/`), not one folder per revision. A fixed path keeps history and blame continuous, and lets CI and docs links stay stable. (Seven projects use folder-per-rev; see 6.3 for why tags are preferred here.)
- **R5. Commit lib tables with `${KIPRJMOD}`-relative paths**, like HackRF and ThunderScope. Never `.gitignore` them (MNT anti-pattern, §3.1).
- **R6. `.gitignore` editor state**: `*.kicad_prl`, `fp-info-cache`, `*-backups/`, `_autosave-*`, `*.lck`, `*.bak`. Reuse Glasgow's and Antmicro's lists ([Glasgow](https://github.com/GlasgowEmbedded/glasgow/blob/main/hardware/.gitignore), [Antmicro](https://github.com/antmicro/jetson-orin-baseboard/blob/main/.gitignore)).

### 6.3 Hardware revision versioning

- **R7. Revisions as annotated git tags plus a GitHub Release**, e.g. `mainboard-r1.0`. In a single-board repo, `r1.0` is enough. This is the Antmicro and BeagleBone pattern. Each release carries the full fab package (6.5), so old revisions stay downloadable without folder copies.
- **R8. Borrow Flipper One's compatibility semantics for every interface that third parties build against** (HAT connector and mechanical envelope, faceplate interface, case mounting): `<MAJOR-LETTER>.<minor>`, where a new letter means "not compatible". Use the same letter in `hat-spec` and in each HAT's "compatible with" field ([Flipper One mechanics](https://github.com/flipperdevices/flipperone-mechanics/blob/dev/README.md)).
- **R9. Stamp the revision on the board from the tag**: put `${REVISION}` in the title block and silkscreen as a KiCad text variable, and pass it in CI with `kicad-cli … --define-var REVISION=<tag>` ([CLI docs](https://docs.kicad.org/10.0/en/cli/cli.html)). Name firmware artifacts by hardware variant, like LibreVNA and NanoVNA-H (§2.4).
- **R10. Use a release branch only if a manufactured revision needs a fix-up** (`rev/r1`). Otherwise `main` = next revision.

### 6.4 Mechanics

- **R11. FreeCAD (`.FCStd`) as the parametric source, STEP as the published interface.** Export STEP, STL (printable parts), DXF (laser/CNC) and PDF drawings **in CI**, not by hand. **UNVERIFIED:** export of everything through headless `freecadcmd` scripts needs a spike; FreeCAD's TechDraw PDF export in headless mode especially needs checking.
- **R12. Track `.FCStd` with LFS and add `diff=fcinfo` as a textconv** for readable diffs ([FreeCAD wiki](https://wiki.freecad.org/Arch_Git)).
- **R13. Publish "envelope" STEP models** of the mainboard, case and HAT bay for accessory makers, in the spirit of Flipper One and Framework, even before the internals are final.
- **R14. Generate fasteners** with the Fasteners Workbench instead of storing screw files ([FastenersWB](https://github.com/shaise/FreeCAD_FastenersWB)). Sync board outlines and models with KiCad StepUp ([StepUp](https://github.com/easyw/kicadStepUpMod)).

### 6.5 What to commit and what to generate

- **R15. Commit sources only.** Generate Gerbers, drill, pick-and-place, BOM, schematic PDF, assembly PDF, STEP/GLB, iBOM and renders in CI from the committed jobset. Attach them to **PR artifacts** (for review) and **GitHub Releases** (for tags). This avoids the stale-output and repo-bloat problems of §3.3.
- **R16. Make outputs reproducible**: pin the KiCad version (container tag) and set `SOURCE_DATE_EPOCH` from the tag commit, like MNT ([build-all.sh](https://source.mnt.re/reform/reform/-/blob/main/build-all.sh)). Store a checksum manifest in the release.
- **R17. Release asset set per hardware tag** (modelled on Antmicro's assets): `…-schematic.pdf`, `…-fab.zip` (Gerber/drill/ODB++), `…-assembly.zip` (BOM, pos, assembly PDFs), `…-step.zip`, `…-board.glb`, `…-ibom.html`, renders, `SHA256SUMS`.

### 6.6 CI

- **R18. Centralize CI in `opendap/ci` as reusable workflows** (`on: workflow_call`), pinned by tag in each repo, like ZMK's `build-user-config.yml@v0.3`. With 7 HAT repos plus the board repos, this avoids drift (§2.6).
- **R19. Hardware PR gate**: `kicad-cli sch erc --exit-code-violations`, `kicad-cli pcb drc --schematic-parity --exit-code-violations`, then `kicad-cli jobset run` for outputs. Add a visual diff (KiRI or KiBot `diff`/`kiri`) as a PR artifact. Use KiBot ([docs](https://kibot.readthedocs.io/en/latest/)) only where `kicad-cli` lacks a feature (iBOM, KiRI, pcb2blender). The pinned image would be `ghcr.io/inti-cmnb/kicad10_auto_full:<version>` ([usage_with_ci_cd](https://github.com/INTI-CMNB/KiBot/blob/master/docs/source/usage_with_ci_cd.rst)).
- **R20. Library CI**: a KLC-style checker on `kicad-lib` PRs, with KiCad's `kicad-library-utils` checks as a base ([kicad-library-utils](https://gitlab.com/kicad/libraries/kicad-library-utils)), plus a visual diff job.
- **R21. Plan HIL early for the instrument HATs**: a self-hosted runner with a reference device, like HackRF (Jenkins plus tester) and LibreVNA (RPi runner). Plan emulation tests (Renode or QEMU) for firmware, like xous-core.

### 6.7 Git LFS

- **R22. Use LFS for binaries that are sources and cannot be regenerated**: `.FCStd`, `.blend`, photos, textures, vendor STEP files in library repos. **Never** put KiCad text files in LFS. **Do not commit** generated outputs or datasheets; link to them instead.
- **R23. Budget for LFS.** The GitHub free quota is 10 GiB storage and 10 GiB per month bandwidth ([docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-storage-and-bandwidth-usage)). Keep `lfs: false` in CI jobs that do not need the binaries, and cache LFS objects. Consider a paid data pack or an external LFS server if `blender-lib` grows. Remember that only 1 of ~30 benchmarked projects uses LFS, so contributors may not have it installed. Document `git lfs install` in every README.

### 6.8 Documentation, licensing, publishing

- **R24. Use one docs generator for all repos.** Sphinx is the de-facto choice for hardware (5 projects, §2.10) and builds HTML plus PDF (MNT handbook). mdBook fits the Rust repos. Choosing Sphinx with MyST Markdown everywhere would keep one toolchain. Publish docs from CI to Pages, like ThunderScope and Glasgow.
- **R25. Licensing**: pick one CERN-OHL-v2 variant for hardware (S, W or P; the benchmark shows S at MNT and P at HackRF, ThunderScope and Flipper One). Use **REUSE** in every repo, as the toolkit already does; no benchmarked hardware repo does, so this would be a differentiator. Add a trademark policy for the OpenDAP name and logo (MNT, Olimex and HackRF pattern), and aim for **OSHWA certification** per product (MNT, Glasgow and BeagleBone are certified).
- **R26. HAT standard repo (`hat-spec`)**: modelled on `raspberrypi/hats` plus MNT `reform-som-template` plus Framework's KiCad templates. Include the spec (Markdown), EEPROM/ID format, envelope STEP, connector footprint and symbol (also in `kicad-lib`), a KiCad starter project, and a conformance checklist. Instantiate each HAT repo from a template in the toolkit's `templates/` folder.

### 6.9 Org-wide libraries (KiCad, FreeCAD, Blender)

- **R27. Use three repos, one per tool**: `opendap/kicad-lib`, `opendap/freecad-lib`, `opendap/blender-lib`. Reasons: different consumers, CI images and sizes, and different LFS needs (KiCad text needs none; Blender is heavy). One multi-tool repo is what produced Antmicro's ~14.5 GB repo (§3.4).
- **R28. Tie the three repos together with a shared part ID** (`<MFR>-<MPN>`, Antmicro's convention) and a small `parts.yaml` or JSON index in `kicad-lib`, which names the canonical STEP and the derived assets.
- **R29. Keep one 3D source of truth per part: STEP**, in `kicad-lib/3dmodels/<lib>.3dshapes/`. Generate WRL (if wanted for KiCad rendering) and GLB (for Blender and the web viewer) in CI. FreeCAD consumes the same STEP; `freecad-lib` holds only parametric `.FCStd` for parts that need it (case-specific, display modules, battery), each with an exported STEP. `blender-lib` holds materials, lighting rigs, scene templates and hand-tuned hero models only; regular parts come from the generated GLB.
- **R30. How KiCad consumers reference `kicad-lib`.** Two options; a recommendation for each audience:
  - **In-org repos: git submodule at `libs/opendap-kicad-lib`, plus lib tables using `${KIPRJMOD}/../../libs/opendap-kicad-lib/…`.** This pins the library per board revision, needs no setup on a fresh clone or in CI, and is HackRF's proven pattern. Updating the library becomes an explicit, reviewable PR (submodule bump).
  - **Third parties (HAT makers): a PCM package** from a **custom PCM repository** (`repository.json` on Pages), built on each `kicad-lib` release, like SparkFun. Ship one variant and document the `PCM_` prefix (SparkFun pain point, §3.11).
  - **Do not** rely on a user-defined `${OPENDAP_KICAD_LIB}` variable as the primary mechanism. SparkFun's `SPARKFUN_KICAD_LIBRARY` works, but it is unpinned and needs manual setup on every machine and in CI. It remains a fallback for people who edit the library and many boards at once.
- **R31. Library versioning**: semver tags on `kicad-lib` (`v1.4.0`). Major = a footprint changed in a way that breaks existing boards. Never edit a released footprint in place; add a new one. Boards pin through the submodule; the PCM package follows releases.
- **R32. Library quality rules**: adopt KLC (with documented OpenDAP deviations) and run the KLC checker plus a visual diff on every PR. Require an MPN, datasheet URL, 3D model and license for each part. Check that each footprint's 3D path uses the library path, not an absolute path.
- **R33. Blender library mechanics**: a directory of `.blend` files in LFS plus one `blender_assets.cats.txt` ([dev docs](https://developer.blender.org/docs/features/asset_system/backend/asset_catalogs/)). Use **Link** in production render scenes, so changes propagate, and **Pack** for archived release renders, so they are self-contained ([prefs](https://docs.blender.org/manual/en/latest/editors/preferences/asset_libraries.html)). Later, it could be exposed as an online asset library by URL (Blender 5.x supports it, but online assets cannot be linked).
- **R34. Library licenses**: CC-BY-SA-4.0 **with an explicit design exception**, like Digi-Key's waiver, so HAT makers can use any license for their own boards ([Digi-Key LICENSE](https://github.com/Digi-Key/digikey-kicad-library/blob/master/LICENSE.md)). Record the origin and license of every vendor 3D model in REUSE annotations, because vendor STEP files often carry their own terms. **UNVERIFIED:** whether specific vendor models (Molex, JST, display makers) allow redistribution; check them case by case.

### 6.10 Simulations

- **R35. Keep `sims/` per repo with inputs only** (ngspice netlists through KiCad's simulator, openEMS setups via [gerber2ems](https://github.com/antmicro/gerber2ems), thermal/FEM inputs). Generate results in CI or locally and attach plots to PRs and releases. No benchmarked project versions simulations in its repo, so this is new ground, and an untested recommendation.
